# Product Principles

## 1. Painkiller over vitamin
Prioritize problems where failure costs money, time, stress, or creates consequences.

## 2. Tuesday test
On a random Tuesday, there should be a reasonable chance the product is useful to the customer.

## 3. Time-to-first-value < time-to-DIY
If the user can solve the problem manually in five minutes, onboarding cannot take seven minutes.

Target first meaningful value in under 60 seconds when possible.

## 4. Value before permissions
Avoid:

Setup -> Setup -> Setup -> Maybe Value

Prefer:

Value -> Permission -> More Value -> More Permission -> Automation

## 5. Progressive onboarding
Suggested progression:
- Anonymous upload/paste
- Account creation
- Watchlist
- Email forwarding
- Notifications
- Gmail/Outlook access
- Additional integrations
- Approved agent actions

## 6. App install is retention infrastructure, not acquisition infrastructure
The initial product should be web-first. Mobile becomes valuable once users need push notifications, approval flows, and recurring engagement.

## 7. Do not sell “AI”
Sell outcomes such as:
- Stop losing money
- Catch costly deadlines
- Recover money owed
- Handle annoying admin

## 8. Persistent context is the moat
The durable product value should come from:
- Structured historical state
- User-specific entities and obligations
- Monitoring
- Permissions
- Workflow history
- Verified outcomes

Not from one-off model responses.

## 9. Trust must be earned
Start by detecting and recommending. Add execution gradually.

Risk hierarchy:
- Low risk: reminders, drafts, information requests
- Medium risk: refund requests, negotiation, cancellations; require approval
- High risk: financial transactions, contractual commitments, government filings, major purchases; require explicit confirmation and stronger safeguards

## 10. Verify outcomes
“Done” is not enough.

Example:
- Cancellation requested
- Confirmation received
- Future billing monitored
- No new charge -> verified closed
- Charge appears -> reopen and escalate

## 11. Explainability by default
For every alert/action, the user should be able to see:
- What triggered it
- What facts were extracted
- What the potential consequence is
- What the agent recommends
- What the agent plans to do

## 12. Same platform, multiple commercial tiers
Do not create bespoke forks for enterprise clients. Use shared product primitives with configurable plans, permissions, governance, and integrations.
